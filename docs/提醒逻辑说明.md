# 提醒逻辑说明

## 1. 位置

- 前端提醒核心服务：`frontend/lib/services/sedentary_reminder_service.dart`
- 首页调试面板：`frontend/lib/screens/app_screen.dart`
- 用户提醒配置页：`frontend/lib/screens/user_info_screen.dart`
- 后端提醒状态接口：`backend/src/main/java/com/kuibuqianli/controller/ReminderController.java`
- 后端提醒服务：`backend/src/main/java/com/kuibuqianli/service/impl/ReminderServiceImpl.java`

## 2. 当前整体思路

当前提醒系统是“前端统一决策，后端提供配置和日志”。

- 前端负责：
  - 久坐计时
  - 本地活动检测
  - 提醒弹窗
  - 调试模拟
- 后端负责：
  - 返回提醒配置和统计状态
  - 记录提醒日志

## 3. 提醒配置来源

提醒配置来自用户信息：

- `remindEnabled`：是否开启提醒
- `remindInterval`：提醒间隔（分钟）
- `remindMaxTimes`：每日最大提醒次数
- `remindAvoidTime`：免打扰时间段

前端启动时会调用后端 `/reminder/status`，同时读取本地当前用户配置，刷新提醒状态。

## 4. 当前提醒触发逻辑

### 4.1 检查频率

- 当前通过定时器每 `10 秒` 检查一次是否需要提醒

### 4.2 提醒判定条件

满足以下条件才会弹提醒：

- 提醒已开启
- App 在前台
- 当前没有提醒弹窗正在显示
- 今日提醒次数未达到上限
- 当前不在“稍后提醒”阶段
- 当前不在免打扰时段
- 当前时间 `>= nextReminderAt`

### 4.3 nextReminderAt 的来源

默认情况下：

- `nextReminderAt = lastMovementAt + remindInterval`

特殊情况：

- 用户点击“稍后10分钟”后：`nextReminderAt = now + 10 分钟`
- 处于免打扰时段时：`nextReminderAt = 免打扰结束时间`

## 5. 当前久坐时长逻辑

久坐时长由下面公式计算：

- `sedentaryMinutes = now - lastMovementAt`

只要发生“有效活动”，就会重置：

- `lastMovementAt = 当前时间`

## 6. 当前风险等级逻辑

基于久坐时长和本轮提醒次数计算：

- 1级：`sedentaryMinutes >= interval`
- 2级：`sedentaryMinutes >= interval + 15` 或本轮提醒次数 `>= 2`
- 3级：`sedentaryMinutes >= interval + 30` 或本轮提醒次数 `>= 3`

对应文案：

- 1级：轻提醒
- 2级：中风险
- 3级：高风险

## 7. 当前活动信号架构

现在已经改成“统一活动信号入口”。

活动来源不会直接改提醒弹窗，而是先转成统一活动信号，再由提醒服务统一处理。

当前活动来源包括：

- 手机传感器
- 手环 Mock
- 手动确认活动
- 完成训练/运动

相关类型：

- `ActivitySignalSource`
- `ActivitySignalType`
- `ActivitySignal`

统一入口：

- `_reportActivitySignal(...)`

## 8. 手机传感器逻辑

这一部分要区分：

- 真机真实传感器逻辑
- 调试面板里的模拟逻辑

### 8.1 作用定位

- 手机加速度现在是“兜底活动来源”
- 不再是单次波动就直接重置计时
- 当手环 Mock 已连接时，手机传感器只记录信号，不直接重置久坐
- 当手环 Mock 未连接时，手机传感器可独立判定有效活动并重置久坐

### 8.2 真机判定方式

先判断是否为明显活动：

- `delta >= 2.0`
- 或 `x.abs() >= 2.6`
- 或 `y.abs() >= 2.6`

如果命中明显活动：

- 最多每 `2 秒` 加 `1` 分

如果没有持续明显活动：

- 超过 `3 秒` 开始衰减分数
- 之后大约每 `3 秒` 掉 `1` 分

这里的分数衰减是由“真实传感器事件流”驱动的，不是业务层单独开一个固定扣分定时器。

也就是说：

- 传感器持续上报事件
- 如果事件不属于明显活动
- 就会走 `_decayActivityScore(now)`
- 根据“距离上一次明显活动过了多久”来计算应该掉多少分

### 8.3 真机有效活动条件

同时满足以下条件时，才判定为一次有效活动：

- `activityScore >= 8`
- 持续活动时间 `>= 15 秒`

满足后会：

- 触发统一活动信号
- 当手环未连接时：重置久坐计时
- 当手环已连接时：只记录手机活动信号，不重置久坐

### 8.4 真机自动活动冷却

当传感器成功识别出一次有效活动后，会进入 `5 分钟` 冷却期。

作用：

- 防止手机仍在晃动时连续多次重复重置久坐计时

注意：

- 这个冷却只针对“传感器自动识别”
- 不影响手动确认或训练完成

### 8.5 调试面板里的手机模拟逻辑

调试面板中的这些按钮：

- `+1 活动`
- `+4 快速累计`
- `模拟15秒有效活动`

本质上不是读取真实传感器，而是直接修改调试状态，用来模拟“手机传感器可能产生的活动结果”。

其中：

- `+1 活动`：人为增加一次活动积分
- `+4 快速累计`：模拟一段较密集的活动输入
- `模拟15秒有效活动`：直接把持续时间补到 15 秒，并把分数补到阈值附近/阈值以上

### 8.6 调试面板里的自动衰减逻辑

因为调试按钮不会像真机一样持续产生传感器事件流，所以专门补了一个“调试自动衰减定时器”来近似模拟真实情况。

规则是：

- 当点击活动模拟按钮后，会启动调试衰减定时器
- 定时器每 `1 秒` 检查一次
- 内部仍然复用真实规则 `_decayActivityScore(now)`
- 也就是说：
  - 不会立刻掉分
  - 仍然要满足“超过 3 秒无明显活动”才开始衰减
  - 衰减节奏仍按真实规则计算

这样调试面板里的分数变化会更接近真机表现，但本质上依然是“人为模拟”，不是硬件真实传感器流。

## 9. 手环 Mock 逻辑

当前还没有真正接入 OPPO SDK，但已经先把 Mock 调试结构搭好了。

同样要注意区分：

- 这部分现在是前端模拟数据
- 不是 OPPO SDK 返回的真实设备数据

### 9.1 Mock 连接状态

- 可以模拟设备连接/断开

### 9.2 Mock 活动规则

#### 步数变化

- `+10 步`：只记录信号，不重置
- 单次步数增量 `>= 20`：判定为有效活动，重置久坐

#### 活动次数变化

- 单次活动次数增量 `>= 1`：判定为有效活动，重置久坐

#### 活动时长变化

- 单次活动时长增量 `>= 3 分钟`：判定为有效活动，重置久坐

#### 运动记录

- 模拟到新的运动记录：直接判定为有效活动，重置久坐

### 9.3 设计目的

这部分是为后续接 OPPO 健康服务 SDK 做准备。

后续接真 SDK 时，只需要把 SDK 读到的数据转成统一 `ActivitySignal`，再交给提醒服务即可。

### 9.4 当前与手机传感器的关系

当前已实现“手环优先模式”：

- 手环 Mock 已连接时：
  - 手机传感器仍可记录活动信号
  - 但不会直接重置久坐
- 手环 Mock 未连接时：
  - 手机传感器恢复为可独立判定有效活动的兜底来源

## 12. OPPO 数据如何接入提醒逻辑

OPPO 数据不会直接操作提醒弹窗，而是统一走提醒服务的活动信号入口。

当前使用的方法：

- `setOppoWearableConnection(bool connected)`
- `ingestOppoActivityData(...)`

也就是说：

- OPPO SDK 真实数据
- OPPO Mock 模拟数据

最终都会统一进入提醒服务，再决定是否重置久坐计时。

## 13. OPPO 与手机传感器的优先级

现在不仅手环 Mock，OPPO 数据也纳入了“可穿戴优先”规则。

- 只要 OPPO 可穿戴连接有效，或当前可穿戴数据源处于连接状态：
  - 手机传感器只记录信号
  - 不直接重置久坐
- 当没有可穿戴连接时：
  - 手机传感器恢复为兜底来源

这能保证后续真机接入时，逻辑仍然一致。

## 14. 无 OPPO 设备时的降级策略

当前系统已经支持没有真机设备时的完整降级。

### 14.1 没有 OPPO 手机/手环时

- 可以继续使用 `Mock` 模式演示和开发
- OPPO Mock 数据仍然会真实进入提醒逻辑
- 本地提醒系统不会因为 SDK 调用失败而崩溃

### 14.2 SDK 调用失败时

调试面板会显示友好的中文提示，例如：

- 当前平台可能不支持
- 可能未安装 OPPO 健康 App
- 可能未完成授权
- 可能未绑定手环或手表
- 当前无可读取健康数据

### 14.3 当前最适合的开发方式

在没有真机设备时，推荐：

- 使用手机传感器调试本地逻辑
- 使用 OPPO Mock 调试可穿戴优先逻辑
- 使用 SDK 模式只验证按钮调用和错误提示是否正常

## 16. 强/中/弱活动信号分工

### 强信号

- 用户手动点击“我已活动”
- 用户完成视频/训练
- 手环检测到运动记录

处理方式：

- 直接重置久坐计时

### 中信号

- 手环步数明显增加
- 手环活动次数增加
- 手环活动时长增加

处理方式：

- 判定为有效活动时重置久坐计时

### 弱信号

- 手机加速度连续活动积分达标

处理方式：

- 作为本地兜底活动来源

## 17. 当前提醒弹窗逻辑

当满足提醒条件后，会弹出提醒对话框。

按钮包括：

- `稍后10分钟`
- `我已活动`
- `立即开始`
- 高风险时：`去视频指导`

用户操作后行为：

- `稍后10分钟`：设置 `snoozeUntil`
- `我已活动`：直接重置久坐计时
- `立即开始`：跳转微运动推荐页，并重置久坐计时
- `去视频指导`：跳转视频页，并重置久坐计时

## 19. 后续接 OPPO SDK 的方向

下一阶段接入 OPPO 健康服务 SDK 时，建议按下面顺序：

1. Android 原生层接 SDK
2. 通过 `MethodChannel` 暴露到 Flutter
3. 先读取：
   - 设备连接状态
   - `TYPE_DAILY_ACTIVITY`
   - `TYPE_DAILY_ACTIVITY_COUNT`
   - `TYPE_SPORT_METADATA`
4. 把真实数据转成统一 `ActivitySignal`
5. 继续复用当前提醒服务，不改主决策逻辑

## 20. 一句话总结

当前版本已经从“单纯手机抖动检测”升级为“统一活动信号驱动的久坐提醒系统”：

- 手机传感器负责兜底
- OPPO Mock / SDK 负责可穿戴接入
- 提醒服务统一判断久坐和提醒
- 真机设备到位后即可继续做 OPPO 联调
